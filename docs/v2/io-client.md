# 联机身体: 客户端接口 io-client (设计草案)

> 用户定、2026-11-01 再次确认: io-client 是我们**自己重新做**的 factorio-mcp, 不是在 factorio-mcp 上改。他的方案只作参考, 不默认是最优解; 他同意我们借鉴和使用他的代码。io-client 做好之前真要联机, 临时用他的 MCP。

## 1. 为什么要自己做
- 第一版的大量故障出在"读和动"这一层: 往箱子塞东西时数量被忽略、取物品一次拿走整箱、设请求要在弹窗里找输入框、导入蓝图受文本框 1024 字限制、窗口最小化时截图卡住、没有变化通知只能轮询。
- factorio-mcp 按他自己的原则只做"透明适配": 不提供任意只读查询, 没有批量和增量读取, 动作只有键鼠时间线和界面控件。这些原则对他的项目合理, 但限制了我们需要的速度和稳定性。

## 2. 做法: 他的代码只是参考, 不默认它是对的
朋友的方案不是最优解, 也不是没有问题。我们每一部分都自己设计, 他的做法作为对照方案之一, 用测试结果决定借鉴哪一种:
| 部分 | 他现在的做法 | 要比较的其他做法 | 怎么判断 |
|---|---|---|---|
| 连接游戏 | 向游戏进程注入代码, 按官方调试符号定位 | 同样注入但换定位方式; 进程外读内存 | 游戏更新后还能不能自动恢复、出错时会不会弄崩游戏 |
| 读世界 | 游戏线程里执行只读 Lua, 按 API 文件开放可读成员, 不支持任意查询 | 批量和增量读取; 预编译常用查询; 变化通知 | 读一片区域的速度、对游戏帧率的影响、会不会读到不一致的数据 |
| 动作 | 键鼠时间线 + 界面控件操作 | 直接发出和键鼠等价的玩家动作 (第 7 节待定) | 成功率、速度、能不能核对结果、会不会和服务器不同步 |
| 界面 | 读控件树, 按选择器点击 | 尽量不走界面, 改走玩家动作 | 设请求、设配方、导入蓝图这类操作的成功率 |
| 宿主和协议 | Kotlin/Native, 单个 MCP 服务 | TypeScript 宿主 + 原生部分; 拆成多个 MCP | 开发和测试速度、和本项目其他部分的契约统一 |
- 先在 M1 用本机客户端连沙盘服务器, 把他现在的 MCP 每个工具测一遍 (成功率、速度、失败方式), 作为基线; 每个替代做法都要用同一套测试证明更好才采用。
- factorio-mcp 已获准使用和改写。借鉴或复用的部分保留出处和署名, 仓库 NOTICE 里写明来源和他的同意; 建议请他在仓库里加一个许可证文件或留一句书面说明, 让开源授权更清楚。

## 3. 规矩
1. **联机不同步的写一律禁止**: 只在本机客户端改游戏状态会导致和服务器不同步, 被踢下线。所有改动都走玩家正常的动作通道, 由服务器校验。
2. **只用公开的东西**: 游戏自带的 API 文件 (`doc-html`)、官方随游戏发布的调试符号文件、Lua API 文档。不用反汇编工具。
3. **只在服务器主人同意时使用**: 向游戏进程注入代码在别人的服务器上可能被视为作弊; 联机只用于服务器主人知情并同意的场合。

## 4. 要做到的
| 类别 | 目标 |
|---|---|
| 读 | 按 API 目录开放所有"可读属性"和"只读方法"; 支持批量 (一次读一片区域的多种实体和字段)、增量 (只返回变化)、分页; 高层读取: 产量统计、物流网库存、电网、孢子、敌人、火车 |
| 变化通知 | 实体建成/损坏/消失、角色受伤/死亡、聊天、警报, 主动推送, 不靠轮询 |
| 动作 | 键鼠和界面控件 + 直接发出和键鼠等价的玩家动作, 两种都做、按服务器切换 (第 7 节, 2026-11-02 已定); 适配层只报"已发出" + 发出时的 tick, "读回核对"放在上一层的行动技能里, 等服务器延迟过去再读 (第 9b 节) |
| 物品和设置 | 按数量取放物品、设请求、设配方、设筛选、导入蓝图 (不受界面文本框长度限制), 每个都核对结果 |
| 画面 | 截图; 窗口最小化时不卡住, 有超时 |
| 聊天 | 读历史、增量读、发消息 |
| 注入说明 | MCP 连接时注入: 能做什么、不能做什么、常见错误; 另带提示模板和资源文档 |
| 稳定性 | 每个工具有回归测试; 游戏更新后自动跑一遍, 报出失效的工具 |

分层原则: io-client 只负责读和动; 寻路、建造顺序、战斗决策这些玩法逻辑放在行动类和计算设计类 MCP, 方便测试和替换。

## 4b. 读内存
读世界有两条路, 都要做, 每类数据按实测定主路 (见架构 10.4):
| | 读内存 (进程外或注入后直接读结构) | 只读 Lua (游戏线程里执行) |
|---|---|---|
| 长处 | 不在游戏线程里跑代码: 不会因为读取弄崩存档 (第一版崩溃的原因是注入的 Lua 读取), 不会造成不同步; 兼容任何模组; 大批量、高频读的开销小 | 跟着 API 文件走, 游戏更新后不用重新定位; 高层统计 (产量、物流网、电网) 现成 |
| 短处 | 结构随版本变, 要按调试符号重新定位; 读到半更新的数据要处理一致性 | 每个接口都要先过不同步测试 (第 5 节); 读大片区域慢、占游戏帧 |
| 规矩 | 只读不写; 每次游戏更新后自动重新定位, 并在本机客户端连沙盘的环境里拿 RCON 真值逐类核对; 定位失败或核对不过就停用那一类读取, 不带着错地址读 | 白名单 + 不同步测试 |

和 factorio-mcp 的设计的关系: 他的 MCP 是透明适配器 (不加游戏逻辑), 方向和架构第 2b 节一致。**更正 (2026-11-02 通读代码)**: 他没有进程外读世界内存, 读世界全靠安全点里的 Lua (原生读取只有界面控件树、聊天、视口、暂停状态、按键绑定, 也是进程内调游戏函数) → 读内存这一路要我们从零做; 每类读取有沙盘真值核对、失败就停用那一类, 这两条规矩不变。

## 5. 只读 Lua 的安全
查询只允许调用 API 目录里标为可读的属性和只读方法, 其余一律拒绝。**白名单不等于安全**: 在客户端里跑 Lua 本身就可能改动客户端的内部状态, 造成和服务器不同步 (2026-10-31 规则审查指出, 待实测)。每个开放的读取接口, 都要先在"本机客户端连沙盘服务器"里做不同步测试, 测过才能在联机上用。目录由 `tools/api-catalog.mjs` 从当前游戏版本生成, 游戏更新后自动跟着变。

## 6. 开发和测试
- 本机沙盘服务器 + 本机客户端连进去: 客户端用 io-client 操作, 服务器用 RCON 读真值对照, 测完可以回档重来。
- 同一套测试先对 factorio-mcp 现在的版本跑一遍, 作为重构的验收基线: 重构后每项都不能变差。

## 7. 待定
1. 动作通道是否允许"直接发玩家动作": 和键鼠产生的动作完全一样、同样由服务器校验, 但更快更准。属于"像玩家一样操作"的边界问题, 要用户定。
   - **已定**: 模拟键鼠和直接发动作两种都做, 按服务器切换。之前的建议原文: 两种都做, **按服务器开关**: 本机沙盘默认直接发动作; 联机服务器先问服主 (他自己的 MCP 就是读内存 + 注入, 多半同意), 不同意就用键鼠。测试先在本机沙盘 (M4 完成标准本来就是本机客户端连沙盘), 进联机服务器只做只读连接测试 (连上、读状态、不建东西)。
2. 宿主语言: 保留他的 Kotlin/Native 宿主, 还是把工具层换成 TypeScript 宿主, 底层仍用他的原生部分。先看完他的代码结构再定。
   - **已定**: 照第 12 节 —— 保留朋友的 Kotlin/Native 宿主, 上层 TypeScript; 读内存走进程外读 + DbgHelp 读 factorio.pdb 定位; 读内存和直接发动作的原生部分用 Kotlin/Native (必要处 C++)。
   - **建议 (2026-11-03, 测试集基线之后; 证据和读内存原生层的方案见第 12 节; 待用户定)**: 保留他的 Kotlin/Native 宿主, 不换 TypeScript 宿主; 我们的 io-client 上层 (测试集、行动技能、读回核对、看门狗、世界模型) 用 TypeScript, 经 MCP 调他的宿主; 要新加的原生能力 (直接发玩家动作、读内存) 做成他宿主里的新工具 (Kotlin/Native + 必要的 C++), 复用他按调试符号定位的代码。读内存走**进程外读** (不在游戏里跑代码) 为主。
3. ~~调试符号随游戏版本变化, 每次游戏更新后要自动重新定位; 定位失败时只降级为键鼠模式, 不能乱读内存。~~ 已定 (2026-11-01): 读内存是主力之一, 规矩见第 4b 节 (自动重新定位 + 沙盘真值核对, 失败只停用那一类读取)。
4. **多开**: 几个游戏客户端同时连同一个服务器, 每个由一个 AI 身体控制, 分头干活。
   - 本机能做: 沙盘已经并行跑过多个实例; 带界面的客户端用单独的配置和数据目录 (观看窗口就是这样开的)。
   - factorio-mcp 是"一个进程对应一个游戏进程", 开几个客户端就起几个进程即可; 要改的是端口和管道名不能写死、启动时指定连哪个游戏进程。
   - 限制: 每个玩家名字要不同; 验证身份的服务器 (大多数公开服) 每个客户端要一个独立的 Factorio 账号; 本机沙盘和不验证身份的服务器随便起名。
   - **2026-11-02 本机实测**: 本机沙盘服务器 (不验证身份) + 两个游戏窗口, 第二个在自己的数据目录 player-data.json 里改名 "AI-2" → 服务器日志 `Refusing connection ... username (MK). UserWithThatNameAlreadyInGame`。**Steam 版的名字取自 Steam 登录, player-data 里改名不生效**, 同一个 Steam 账号开几个窗口都叫同一个名字, 只能连进去一个 —— 不验证身份的服务器也一样。游戏命令行没有不走 Steam 身份的参数 (`--help` 查过)。
   - 核查 (游戏自带语言文件, 2.1.24): 设置 → 其他 → **"局域网玩家名"**, 说明原文 "未登录时在局域网游戏里用的玩家名。**登录后它就是你的 Factorio 用户名, 不能改**"; 同一栏有"退出登录"。Steam 版启动就用 Steam 自动登录 (程序里有 steam-login-success), 而且玩家数据存在 Steam 云存储 (本机 AppData 里没有 player-data.json, 客户端日志有 "Steam Storage Quota"), 所以在窗口自己目录里写的名字被盖掉 (推断, 和实测一致)。→ 能自己设名字, 但要**没登录**的客户端: 最稳的是 factorio.com 的独立版 (不走 Steam, 已购买的账号能免费下载, 要用户登录下载), 第二个窗口用它、不登录、设局域网玩家名 "AI-2", 连朋友这种不验证身份的服务器 (待测)。
   - **多开实测成功 (2026-11-02)**: 用户在 factorio.com 绑定 Steam 后下了完整独立版 (2.1.24 + 太空时代, 和 Steam 版同版本), 解压到单独目录; 第二个窗口用它 + 自己的数据目录 + 不登录 (player-data 不给令牌、名字 AI-2) → 本机沙盘服务器上 `MK` 和 `AI-2` 同时在线, 服务器日志两个都 PlayerJoinGame。联机服务器不验证身份, 同样做法应能进 (进之前先征得他同意第二个玩家)。
   - 推论: ① AI 用你的账号进朋友服务器时, **你自己就不能同时用这个账号在里面** (用独立版 + 别的名字就不冲突); ② 多开要么每个身体一个账号, 要么用 factorio.com 的独立版 (不经 Steam; 未登录时名字取 player-data, 待测, 要你登录 factorio.com 下载) + 服务器关掉身份验证 (服主定, 最好配白名单)。③ 先一个身体做 M4, 多开不挡路。
   - 总控要跟着改: 调度器把任务分给不同身体 (一个建造、一个巡逻补给), 加规矩"两个身体不在同一块地方同时施工"; 先在本机沙盘里两个客户端试。

## 8. 第一版的工具坑 (M4 对照用, 2026-11-02 清点)
第一版知识库 (2026-10-28 ~ 10-31, 联机用 factorio-mcp 操作) 里记下的 19 条操作坑。每条分清是**游戏规则** (换什么工具都一样, io-client 要照着做) 还是**工具用法** (第一版用的 MCP 或第一版后台自己的毛病, io-client 要从设计上绕开)。都没在 2.1.24 沙盘里重测, 做 M4 回归测试时逐条变成用例。游戏知识部分见 [research/players/v1-knowledge.md](research/players/v1-knowledge.md)。

| # | 现象 | 原因 | io-client 怎么避免 |
|---|---|---|---|
| 1 | 左键点实体没打开窗口, 却把手里的东西放下或用掉了; 没有窗口时按 ESC 打开了主菜单; 单人模式下有的窗口会让游戏暂停, 暂停时键鼠时间线报错, 界面操作仍有效 | 游戏规则: 开实体窗口的前提是手里为空; ESC 在没窗口时开主菜单; 单人时科技窗口、主菜单会暂停 (实体窗口暂不暂停待带界面客户端核实) | 每个"打开窗口"动作先清空手 (核对光标为空); 关窗口前先读当前打开的窗口, 没有就不按 ESC; 动作前读一次"是否暂停" |
| 2 | 放蓝图、拆除标记一件都没落下, 工具却报成功 | 游戏规则 + 工具用法: 玩家在远程视图里时, 屏幕坐标按远程镜头算, 目标不在屏幕上 | 动作前读玩家控制器类型, 在远程视图就先退出 (或等用户退出); 每个放置动作做完读回实体核对 |
| 3 | 往别人正在用的角色上发键鼠, 和人抢操作 | 工具用法 (协作): 同一个角色可能被用户或队友接管 | 每个动作前读控制器类型、空闲时间、缩放; 有人在用就只读 |
| 4 | 物品转移出错: 往箱子塞东西忽略数量、整组塞进去, 取东西一次拿走整箱; 想拿背包里的弹匣, 却先匹配到了枪的弹药槽 | 工具用法 (第一版用的塞取接口、按控件名找格子); 弹药槽和背包格在界面里是同一种控件 (游戏界面结构) | 按物品名和数量取放, 塞不下要报实际数量 (同沙盘的 lab.insert 规矩); 不按控件名找格子; 做完读回双方库存 |
| 5 | 崩溃恢复和聊天: 读档后自动存档计时从读档那一刻起算; 主菜单载入最新存档时, 若最新的是 .tmp 文件会弹"文件无效或损坏", 要先点确认; 聊天框开关键是 Esc 下面那个键 (GRAVE), 聊天框开着时 Shift+左键地图能插入可点的 [gps] 坐标, [planet=…] 标签显示成星球图标 | 游戏规则 | 恢复流程按这两条写 (先关确认框再选存档); 聊天里的坐标和星球一律用富文本标签, 不手打 |
| 6 | 设优先集货箱 / 物流接驳站请求时找不到输入框: 2.1 的请求弹窗是"最小 / 最大"两个输入框, 选择器要带上当前文字才定位得到, 窗口位置每次会挪 | 游戏界面 (2.1 改版) + 工具用法 (按坐标和控件名点) | 设请求做成一个动作 (物品、最小、最大), 做完读物流分组核对; 不依赖窗口坐标 |
| 7 | 电路设置: 没接线的实体窗口里没有电路区; 接线、设常量运算器、判断运算器条件、机械臂"启用条件"都要多步点界面 | 游戏规则: 先接线才出现电路设置区 | 接线和电路设置做成动作 (连哪两个实体、哪种颜色; 条件和输出), 做完读控制行为核对 |
| 8 | 时刻表界面在远程视图里打开, 关窗只能点右上角关闭按钮; 期间角色不能走路 | 游戏规则 + 工具用法 (第一版靠点界面编时刻表) | 时刻表、中断按结构写入后读回 (沙盘里已知: 时刻表要用 get_schedule().set_interrupts, 整表赋值会丢中断, lab.md #29); 联机时只能走界面, 关窗后核对控制器类型回到角色 |
| 9 | 蓝图: 拆除 / 升级规划器从快捷栏拿是临时的 (按 Q 就销毁), 导入的蓝图是真物品、每导入一次多占一格背包; 背包满时导入、放置、拆除都静默失败 (手上的东西放不回背包) | 游戏规则 (物品性质) + 工具用法 (失败不报错) | 导入前核对手空、背包有空格; 用完的蓝图回收或删除; 每个动作读回光标物品类型 |
| 10 | 蓝图字符串 ("0" + base64(zlib(JSON))) 经导入框文本输入一次最多约 1024 字, 大蓝图要切块, 切块后铁轨整块偏位 | 工具用法 (按文本框逐字输入); 偏位是游戏规则 (普通放置按外框中心对位) | 导入走"拖文件进窗口"或导入窗口的"粘贴"按钮 (docs/verify.md "游戏外设计 → 精准导入"); 一律用绝对吸附 (facts blueprint.absolute-snapping.exact) |

## 9. factorio-mcp 代码通读 (2026-11-02, 本机克隆 0.0.5 = 第一版用的那一版; 只读, 没编译没运行)
 之前只按他的设计思路做过比较, 这次逐文件读了一遍 (私人笔记里有带文件和函数名的完整地图)。要点:
1. **结构**: Kotlin/Native 宿主 (MCP 服务) + C++ 注入库 (远程线程加载进游戏)。两边只靠**按进程号命名的共享内存 + 互斥锁**通信, 宿主每 10 毫秒轮询; 不开端口连游戏。
2. **定位**: 每次挂上都按游戏自带的调试符号文件现场找函数和偏移, 不存偏移表; **每类功能单独判断成败**, 游戏更新后哪个符号对不上就只停那一类工具 (借鉴)。
3. **读世界**: 全靠在游戏主线程每帧更新界面的安全点, 用场景脚本的 Lua 环境执行只读代码; 可读成员按 API 文件生成白名单 (白名单里缺进化度那个方法 → 第一版读不到进化度的原因)。查询上限 (每边 ≤128 格、≤512 个实体等) 是**他自定的工作量上限**: 每次读取都挡着一帧, 共享内存又是固定大小; 不是游戏规则。
4. **发动作**: 键鼠不是操作系统层的模拟, 而是在进程里构造游戏自己的输入事件 (不需要窗口焦点); 界面点击直接调控件自己的事件函数。**"直接发玩家动作"已有现成样板**: 他发聊天就是构造"写入聊天"的输入动作, 交给游戏自己的联机同步入口, 服务器照常校验。2.1.24 的调试符号里约有 330 种输入动作 (导入蓝图字符串、设物流请求、设配方、按格转移物品…) → 可以根治"蓝图 1024 字"、设请求、取放错格这几类坑; 每种动作的数据布局和服务器校验条件都要在沙盘里核实。
5. **第一版大坑的根源**: 不检测"正在存档" (只判断是否在加载地图)、工具不设超时、截图按原尺寸不缩、所有请求排一个队 → io-client 要在注入端补存档检测, 加超时、截图缩放、动作后读回核对。
6. **导入蓝图的两条路** (第一版 1024 字的根源是他逐字发按键、缓冲区写死 1024): ① 字符串放进系统剪贴板, 在导入框里发一次 Ctrl+V (游戏自己读剪贴板, 和人的操作一样); ② 直接发"导入蓝图字符串"动作。蓝图编辑器 (bp render / link) 管游戏外的设计和看图, 和这一步配合; 两条路 M4 都在沙盘里测。
7. **可以直接借鉴**: 按调试符号定位 + 按功能单独降级; 安全点 + 命令状态机 (MCP 崩溃后先收拾上一个请求, **绝不重放不确定的动作**); 游戏事件层的键鼠和松键逻辑; API 文件生成目录 + 只读白名单; 他的验收场景每 300 tick 强制全量校验 CRC, 可以搬来做不同步测试。
8. **多开**: 不用改他的代码: 端口可配 (`--http-port`, 0 = 随机), 共享内存和锁名都带进程号; 每个客户端起一个 MCP、按进程号挂上即可 (他说的"一个 MCP 进程对应一个游戏进程"就是这个意思, 同时起几个不打架)。限制: 同一个游戏进程只能加载同一路径下的注入库。
9. **许可证**: 他的仓库和 npm 包都没有许可证文件或字段。**factorio-mcp 的代码已获准复制。** 复制和改写的部分保留出处和署名 (仓库 NOTICE 写明来自 factorio-mcp 仓库 和对应提交)。
10. **宿主语言** (第 7 节第 2 条): 扩展他的 Kotlin 宿主, 还是换 TypeScript 宿主 (底层仍用注入库) —— 先拿他现有的 MCP 对本机沙盘跑一遍基线测试 (M4 完成标准本来就要新旧各跑一遍), 再定。

### 9b. 他的两条"反直觉"规矩, 想清楚了再定
他的规矩原文在仓库的 AGENTS.md 和 tools.md:
1. **不加工具超时, 只许测试用的看门狗**。原因 (从他的取消和清理规矩推出): 动作在游戏里是分帧执行的 (按住的键、鼠标拖动、界面捕获、钩子), 超时直接放弃会把游戏留在半截状态 (键没松、界面捕获没释放、注入库还在跑), 比卡住更糟; 所以只有"配合式取消": 发取消, 等它自己收尾、松开按键、释放捕获后才返回。→ **我们照做**: 适配层不加超时; 在它上面加**看门狗**: 发现某个工具久久不回 → 先记录和告警 → 发配合式取消 → 取消也不回才按"游戏卡死"走崩溃恢复 (重启游戏 / 重连)。看门狗管"卡住了怎么办", 不在半截动作里强行打断。
2. **动作只报"已发出", 不读回结果**。原因 (他的原文): 联机时动作要经网络到服务器、在之后某个 tick 才生效; 客户端还有**预测和回滚**, 刚看到的效果可能被服务器改掉或撤销 —— 发完马上读回, 读到的可能是假的 (假成功或假失败); 读回还要猜"该读哪个实体、哪个格子", 那是游戏逻辑, 他坚持透明适配不替模型判断 (和我们架构第 2b 节"决定归模型, 真相归工具"一致); 他也规定"不要盲目重放结果不确定的修改"。→ **我们照做, 但分层**: 适配层 (io-client) 保持只报已发出 + 返回发出时的 tick; 核对放在上一层的行动技能 (M5): 等服务器确认的延迟过去 (按 tick 算), 用一次聚焦查询读回, 和预期比; 对不上就交给模型判断, 不自动重试、不盲目重放。原来第 3 节写的"做完就读回核对"改成指行动层, 不是适配层。
3. 所以第 9 节第 5 条里"不设超时""只报已发出"不算他的毛病, 是分层问题; 真正要我们补的是看门狗、存档检测、行动层的核对、检测用户接管。

### 11j. 把模组做成游戏外的内存外挂

**什么时候用 (`src/io/backend.ts`)**: 联机服务器没开 RCON 才走外挂; 本地存档、新地图、服务器明确开了 RCON 都走 RCON + 模组。服务器开了 RCON 但没装模组时 RCON 调不到模组, 也走外挂。联机的群可以选: 自动 (默认) / 内存外挂 / RCON, 见第十块。所以沙盘里的外挂只是拿真值核对用, 本地的班不走它。

**思路**: 游戏里不跑任何代码, 服务器只看到普通玩家, 所以不会不同步。模组的活拆三块搬到游戏外: 读世界 = 进程外读内存; 账本 (队列、消息、教训、看板) = 本机文件; 动作 = 发玩家操作 (不改内存, 速度受真人同样的限制)。模组直接只在客户端跑不行: 脚本要所有机器一起跑, 只在一台跑立刻不同步。

**量的规模** (2026-11-06, `mods/agent-harness-party`): 303 个 Lua 文件 14.8 万行, 213 个命令, 用到 285 种游戏方法 (读 155 种)、617 种属性、15 种事件。班次 10-16-30 去掉轮询后 7440 条请求 81 种命令, 前 30 种占 95%。

**第一块: 全地表实体 ✅ 沙盘** (`tools/memread/entities.py`, `npm run io:memcheck`): 指针链 global → game → map → surfaces → 区块表 (`InfiniteRectangle<Chunk*>`) → `Chunk.advancedTiles` (16×16 格, 每格一条 `EntityConnector` 链表) → `Entity` (原型名、位置) / `EntityWithOwner.unitNumber`; 大实体跨几格按指针去重。布局从 pdb 现场取, 独立版也带 factorio.pdb。**结果 (2026-11-06 00:28, 班次 10-16-30 存档, 独立版客户端)**: 暂停时 RCON 17582 个、内存 17582 个, 名字 + 位置逐个相等, 编号 1492 个全对, 丢弃 0, 242 毫秒 (Python, 进程外, 不占游戏帧; 只读 Lua 读 3600 个要 341 毫秒且挡游戏约 35 毫秒); 跑着连读 5 次丢弃 0、约 225 毫秒, 对真值只有 20 条鱼位置不同。两个坑: ① pdb-dump 深度 1 会撞上嵌套里的同名成员 (`Game.map` 读成 +8), 取偏移用深度 0; ② `global` 两种读法要靠 `map.game` 回指判定, 只看指针像不像会选错。

**还没做 / 不确定**: 研究、产量统计、污染、电网、已探区块都还没读。上真服只核过位置和背包, 实体这块没核。

**搬法定下来**: 混合。读 = 模组 Lua 原样 + 假接口接内存 (功能和字段跟着模组, 上游更新不用手动跟); 动作 = 重写常用命令 (走路、建造、搬运、挖、手搓…, 真班 30 个命令占 95%), 发玩家操作。保留不了的: 脚本造角色 (每个 AI 要一个真客户端, 独立版多开实测过两个); 要重写的: 寻路、能不能放 (引擎函数); 会不全的: 靠事件记的历史 (谁建的、被谁打)。

## 12. 宿主语言和读内存原生层: 建议和证据 (2026-11-03; 第 7 节第 2 条, 待用户定)
 (第 4b 节: 读内存和只读 Lua 两条路都做, 每类数据按实测定主路; 只读不写、按调试符号自动重新定位、沙盘 RCON 真值逐类核对、核对不过就停用那一类)。朋友的原生部分只读界面 / 聊天 / 视口 / 暂停, 读世界全靠安全点里的 Lua (第 4b 节更正) → 读世界内存这一层是我们自己做的。这一轮没实现读内存, 只给方案和证据。

**证据**
1. 调试符号: 游戏自带 `factorio.pdb` (2.1.24 Steam 版, 461MB, 和 factorio.exe 同目录)。朋友用 Windows 自带的 DbgHelp (`SymLoadModuleEx` / `SymEnumSymbols` / `SymGetTypeInfo`, 按 TI_GET_CHILDRENCOUNT 等逐个取结构成员) 现场找函数和**结构成员的偏移**, 不存偏移表, 按功能单独判断成败 (`DebugSymbols.kt` 549 行、`DebugTypes.kt` 387 行、`PdbTypeStream.kt` 354 行等)。他用这套读聊天、按键、界面控件的内部结构, 在 2.1.24 实测可用 (T14b 聊天、T7/T11 键鼠、T7e/T9 界面都过) → **读世界内存要的结构布局 (地表、区块、实体、物品栏) 也能这样拿**, 方法有现成实证; 具体的结构 (实体列表怎么串) 待在沙盘里逐类核对。
2. 他代码的分布 (5489375): 通用部分 Kotlin 5.6k 行 (工具契约、生命周期、取消、只读 Lua); Windows 平台 Kotlin 4.5k 行 + C++ 3.3k 行 (调试符号、注入 `CreateRemoteThread`、共享内存通信、`ReadProcessMemory`、输入和界面的内部布局); Linux 平台 46k + 17k 行 (Linux 没有类型信息, 靠反汇编推布局, 我们先只做 Windows)。**读内存要的三样 (打开进程、读调试符号拿布局、读进程内存) 他 Windows 那部分都已有**。
3. 只读 Lua 这条路的代价 (11b): 读 3600 个实体 341 毫秒、841KB, **每次挡住游戏约 35 毫秒 (2.1 帧)** (T2d); 第一版唯一一次崩溃发生在自动存档时的高频 Lua 读 (T12 现在 0 失败, 但没复现不等于不会); 他自己记录过"看起来只读的 Lua 接口也能改状态 (can_insert、翻译请求曾导致不同步)" (AGENTS.md)。→ 大批量、高频的世界模型读取 (实体位置 / 名字 / 状态码、背包、手上) 正是读内存值得做的地方; 低频高层的 (科技、电网、统计、进化度) 用 Lua 现成接口更省事。这就是 11b 表里"以后主路"的依据。
4. 走 MCP 的开销小: status 一来一回 5~25 毫秒, 小查询 15~60 毫秒 (11b)。慢的是界面驱动的动作 (T8 放 37 个要 9.5 秒、取 25 个 14 秒, 一次右键加读回约 190~260 毫秒) → **换宿主语言解决不了速度, 要靠直接发玩家动作** (原生层, 第 9 节第 4 条)。
5. 他宿主的生命周期实测可靠: 挂接 / 断开 / 退出 7/7、看门狗取消后键松开且后面请求恢复 2/2、不绘制时截图立刻报错 6/6 (11b)。
6. 本机能编他的工程: JDK 25、VS 2022 构建工具 (MSVC 14.44、CMake、Ninja)、Kotlin/Native 2.4.10 预编译包都在 (没实际编过, 待核实)。

**方案**
1. **读内存走进程外读为主**: 我们自己一个只读进程 (或他宿主里的新工具) 用 `OpenProcess(PROCESS_VM_READ)` + `ReadProcessMemory` 读游戏内存, 布局用 DbgHelp 从 factorio.pdb 现场取 (和他一样不存偏移表, 校验类型、宽度、边界)。好处: 不在游戏里跑代码 → 不会弄崩游戏、不会不同步、存档时也能读、不挡游戏帧。难处: 游戏线程同时在改 → 会读到半更新的数据; 办法是"读前读后各读一次游戏 tick, 不一样就重读" (类似顺序锁), 还要批量读整页减少调用次数 —— 都待沙盘实测。
2. **注入后在安全点里读原生结构** (他已有安全点钩子) 作第二选择: 数据一致、快, 但在游戏线程里跑, 布局错了会弄崩游戏 → 只用于进程外读保证不了一致性的那几类。
3. **语言**: 读内存和直接发动作的原生部分用 Kotlin/Native (+ 必要的 C++), 放在他宿主的 Windows 部分旁边, 复用他的调试符号、进程、注入、共享内存代码 (约 1.3k 行调试符号代码不用重写); 不另起一个 Rust / C++ 进程 (要重写同一套定位, 还多一个进程), 也不用 TypeScript 直接读 (JS 没有成熟的 PDB 库; 调 DbgHelp 要 FFI, 等于重写他那一层)。**上层 (测试集、行动技能、读回核对、看门狗、世界模型) 用 TypeScript**, 经 MCP 调宿主, 和本项目其他部分 (沙盘、大脑链路) 一个语言。
4. **验收**: 读内存那一路实现 `IoReader` (第 11 节), `npm run io:suite -- --reader mem` 跑 T2~T6 (加 T12 存档时读、T2d 帧率), 和只读 Lua 那一路对同一份 RCON 真值逐类比, 每类按"准不准、快不快、挡不挡帧"定主路, 核对不过就停用那一类; 每次游戏更新后自动重跑。
5. **和 factorio-mcp 的关系**: 新工具先在我们的分支 (已获准复制, NOTICE 署名) 里做, 每加一个都按 factorio-mcp 的规矩 (只读、动态定位、按功能降级、不改已有工具的契约); 做成熟的再提给上游 —— 读内存这类"原生读世界"和 factorio-mcp "优先 Lua API"的取向不完全一样, 收不收由上游定。
**代价和风险**: 我们要同时维护 TypeScript 和 Kotlin/Native 两种语言、Gradle + MSVC 的构建; 读内存的结构布局随游戏版本变, 每次更新都要靠沙盘真值重新核对 (第 4b 节规矩)。
