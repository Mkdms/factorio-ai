# 计算器 calc (M3)

> 2026-11-02 起。路线图 M3: 计算设计类 MCP 的第一块。完成标准: 句芒"生物核心"在沙盘里连续跑 1 小时, 实测产量和计算相差不到 10%。

## 用法
```bash
npm run calc -- plans/gleba-bio-core.json
```
方案文件: `targets` (物品 → 每分钟净产出)、`recipes` (用到的配方 → 机器、插件、分享塔、品质、研究产能、燃料)、`imports` (可以从外面进的; 不给就是"配方都不产出的都能进")。输出每个配方要几台 (小数和取整)、每分钟吃 / 出、燃料、电; 从外面进的、多出来的 (副产物)。名字一律官方中文名。

## 做法
- 数据全从本机原型导出读 (`src/calc/data.ts`), 字段默认值照原型 API 文件 (配方时间 0.5 秒、类别 crafting、产能上限 300%、产能忽略量默认 = 统计忽略量)。
- 有循环的链 (句芒营养素喂生物室、生物室又做营养素; 细菌培养) 和副产物用线性规划解: [yalps](https://github.com/IanManske/YALPS) (MIT), 不自己写求解器。
- 规则 (`src/calc/solve.ts`): 每次产出 = 期望量 + (期望量 - 产能忽略量) × 产能; 每台每分钟做 = 60 × 机器速度 × 品质倍率 × (1 + 速度) / 配方时间; 分享塔每座 = 插件效果 × 分享效率 × 递减表[塔数 - 1]; 产能夹在 [0, 配方上限], 不许产能的配方不吃; 速度、耗能不低于 -80%; 烧燃料的机器每分钟燃料 = 耗能 × (1 + 耗能加成) ÷ 燃烧效率 × 60 ÷ 燃烧值。

- **腐坏批量** (验收时沙盘发现的): 链里会坏又被用掉的东西 (营养素、果泥…), 产出它的配方每分钟至少做 批量 ÷ 保质期 个 (营养素一批 60、保质期 5 分钟 → 至少 12 / 分钟); 消耗比这少时多出来的会坏, 结果里单独列"腐坏浪费"并算进用料。按全新算 (原料继承的新鲜度不算), 偏乐观一点。

## M3 验收 (2026-11-02 ✅)
`experiments/m3-bio-core.ts` (`m3.gleba-bio-core.hour-vs-calc`): 两台组装机2型加工玉玛果和果冻果, 直塞一台生物室做生物结晶; 生物结晶进中转箱 (多于 10 个就运走), 另一台生物室做营养素, 环形带送燃料 (带子 + 机器里营养素一共 < 20 才放生物结晶, 过滤臂挑变质物); 种子和变质物用过滤臂清走。**计算 35.0 / 分钟, 沙盘 1 小时实测 34.6, 差 -1.1%**, 每 10 分钟 34.0~35.0 稳定。
调了五轮, 每轮都是真实的句芒问题:
1. 配方没解锁 (沙盘阵营): 临时解锁、测完还原。
2. 营养素死头带: 营养素一批 60 个远超消耗, 堆在带子上 5 分钟就坏, 尽头的没人用只能等坏, 第 50 分钟两台生物室断燃料 (-22.8%) → 环形带 + 过滤臂挑变质物。
3. 限产只看带子: 出料臂一次搬 1 个, 60 个要搬 26 秒, 期间限产臂继续放料, 营养素生物室接连做好几批堆在出口里变旧 (出口营养素坏 49%, -12.8%) → 营养素生物室也接进电路读内容物。
4. 中转箱越攒越旧 (营养素继承原料新鲜度): 只留 10 个。
5. 计算器原来不算批量浪费 (预测 35.6): 加了上面的腐坏批量规则 → 35.0。

## 品质和待机耗电 (第十九批 ✅, `experiments/calc-rules.ts`)
- 电力机器没写待机耗电时 = 满负荷的 1/30 (组装机2型 5000W, 引擎读数和电网统计都是)。
- 机器品质速度 × (1 + 0.3 × 等级), 等级 普通 0 / 精良 1 / 稀有 2 / 史诗 3 / 传说 5 (组装机2型 0.75 → 1.875)。
- 插件品质**只放大正面效果**, 每级 +30%, 向下取整到 0.1%: 传说速度插件 3 速度 +125%、耗能仍 +70%; 传说产能插件 3 产能 +25%、减速和耗能不变。方案里写 `"speed-module-3@legendary"`。
- 分享塔品质每级 +0.2 分享效率 (原型字段): 普通 1.5、传说 2.5 (×1.67)。方案里 `beacons.quality`。

## 和 Factory Planner 对照 (2026-11-04)
- 做法: `tools/patch-fp.py` 把 Factory Planner (ClaudeMetz/FactoryPlanner, MIT) 复制到 `mods/factoryplanner` (不进仓库) 并加一个 remote 接口 `fp-interface.solve_packed` (不开它的界面, 直接把打包好的工厂交给它的求解器); `npm run calc:crosscheck -- plans/x.json …` 起沙盘 (开窗口: FP 要有玩家) 两边各算一次, 并排比每个配方的机器数 (`src/calc/fp.ts`, 单元 test/calc-fp.test.ts)。**FP 只在沙盘当裁判, 大脑用的 ./calc 还是我们的离线程序, 朋友服务器上照常能用。**
- 踩过的坑 (打包格式): FP 内部数量按秒 (界面才乘时间尺度) → 产品 amount = 每分钟 ÷ 60; 没类别的原型 (配方、品质) 不能写 `category` 字段 (它的 find 要 nil, 空字符串查不到, 否则校验失败、修复时把线全删); 机器不写类别让它按配方类别找; `require` 只能在加载时, 补丁里的 solver 是它的全局表。
- 结果 (2026-11-04): 红瓶 + 绿瓶 30/分钟 (9 条配方, 组装机 2 型 + 电炉) **两边 0% 差**; 句芒生物核心 (营养素循环, 生物室烧营养素, FP 用 simplex 求解器) 4 条配方 **0% 差** (我们 0.853 / 0.341 / 1.023 / 0.009 台 = FP)。也就是说在"机器数"这一层, 我们的计算器和 FP 一样准; FP 的腐坏批量浪费不单列, 我们多算这一项。
- 第二轮 (插件 / 分享塔 / 品质也转进打包, `plans/crosscheck-modules.json`): 组装机 3 型 + 4 个产能插件 2 + 8 座分享塔 (速度插件 3) 1.332 台、稀有组装机 2 型 + 速度插件 0.56 台、电炉 + 2 个产能插件 5.124 台、2 座分享塔 0.44 台、传奇速度插件 3 + 品质插件 2 0.303 台 —— **5 条全部 0% 差**。三个方案 18 条配方两边一致。
- 打包顺序的坑: FP 的顺序求解器只让下面的线供上面的线, 线要按"最深的消费者再往下一层"排 (铜板同时供红瓶和铜缆就得排在铜缆下面), 否则 FP 把原料当外购; 有循环的链 (生物核心) 用 `--solver simplex`。
- 还没转进 FP 的 (对照时标 "没转进 FP"): 固定台数、燃料选择; 腐坏批量浪费 FP 不单列。
