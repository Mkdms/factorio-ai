# 蓝图数据集

> 2026-11-02 起: 模型没有现成的蓝图训练集, 我们自己做一个。

## 用来做什么
我们改不了 Claude 本身的参数, 数据集的用处是:
1. **设计时检索示例**: 设计熔炉区之前, 从库里取 3~5 个实测过的同类好设计放进提示词 (最快见效)。
2. **考卷**: 给定任务 (例: 每秒 15 块铁板), 用库里的最好成绩做基准, 给 AI 的方案打分 (评测场)。
3. **将来训练专用小模型** (布局打分 / 生成, 开源模型): 数据现在就按这个标准存。

## 分档
1. **精品**: 我们自己用积木 + 搜索 + 求解器 (例: Factorio-SAT 求平衡器 / 紧凑排布) 找出、沙盘按指标排第一的设计。群友以后愿意给的设计和思路仍然收 (只存本机, 思路进 knowledge/patterns/)。
2. **参照**: 公开蓝图站 / 合集 (Brian's 等) —— 当平均水平和反例, 不当标准答案; 用来测检查器、测覆盖面、给"精品"做对比。
3. **指标** ("精品"要能量出来): 产量 / 占地、用料、能不能直接平铺扩展、耗电、长时间跑会不会堵 (沙盘实测)。

## 一条记录 (`lab-data/datasets/index.jsonl`, `src/dataset/ingest.ts` 的 BpRecord)
出处、许可、地址、文件、名字、游戏版本、建筑数、大小、各建筑和配方的数量、认不出的建筑名 (模组 / 旧版本)、静态检查结果 (错误 / 警告按类计数; 有认不出的建筑就不查)、粗分类 (火车站、冶炼、电路、发电…)、收录日期。

## 标签分三层 (只有后两层能当"好坏")
1. **静态检查** (现在就有): 2026-11-02 第一次跑, 报得最多的是地下带没配对 615、管道口空着 510、机械臂对空地 260 —— 社区蓝图多是拼接用的模块, **边缘没接上是设计如此, 不能直接当错**; 1.1 旧铁轨的网格 / 对位报错也多 (rail-off-grid 112), 检查器对旧版本要另算。
2. **沙盘实测** (`npm run dataset -- measure`, 2026-11-02 第一版不喂原料): 放进沙盘 (`bp try` 的流程)、按电网接电、跑 5 秒, 记建成多少、各状态多少、引擎核对 (不在电网里、地下带没配对、流体孤立、铁轨尽头、信号 / 车站没接轨)。第一次跑: 布局类 151 张里 **145 张完整建成**、5 张部分建成、1 张导入失败; 列车编组 47 张 (只有车辆, 要先铺轨) 跳过; 16 张有不在电网里的用电建筑 (多是靠相邻模块供电的拼接块)。下一版: 给入口接永续料源、出口接收料箱, 测产量、耗电、堵不堵。
   - 检查器的"区段放不下列车"在 Brian's 火车站上报了 81 次, 因为标准列车临时按 4 节算, 他的多是 1~2 节 → 标准列车长度要先定, 这条才有意义。
   - **喂料实测** (`npm run dataset -- feed`, 2026-11-02, 模组 `feed_setup` / `feed_stats`): 只测第二层完整建成、有机器的布局。全在引擎里自动判断, 不手写每张的接法:
     1. **上什么料**: 每条传送带的起点往下游追 (带子、地下带、分流器), 看哪些机械臂从这条带取货、喂给什么配方 → 原料减去蓝图里自己能做的 = 这条带要的料。1~2 种两道各一种; 3~4 种有煤就每个喂料口一道煤、另一道放矿, 分流器两半各分一半; 5 种以上不支持。烧煤的机器 (石炉、钢炉) 自动加煤。分流器 / 地下带当起点的, 在它背后接一格同级传送带当喂料口 (分流器的车道线插不进)。
     2. **炉子做什么**: 炉子放下时没配方, 先看它的产物被下游谁要 (出料臂 → 带子往下游 / 机器 / 箱子), 推不出再看蓝图图标, 最后默认铁板。
     3. **收料**: 带子尽头的上游有机械臂往上放东西的, 尽头每 2 tick 收走"蓝图里做出来的东西" (原料留在带上 —— 第一次试跑全收, 喂进去的料直接被收走、机器反而缺料); 只往里放的箱子 = 收料箱 (每秒清空计数), 只往外取的箱子 = 料箱 (每秒补满)。
     4. **准备**: 沙盘阵营只解锁全部配方 (不做研究, 研究会加机械臂容量等, 改吞吐); 不在任何电网里的用电建筑按数据补配电站 (靠相邻模块供电的拼接块), 记 `powerFixed`。
     5. **测**: 预热 60 秒, 测 180 秒 (分两半): 每种产物每分钟产量 (游戏的物品生产统计)、理论上限 (每台机器的实际速度 × (1 + 产能) ÷ 配方时间, 含插件和分享塔)、**效率** = 成品 (蓝图里不再被用掉的产物) 实测 ÷ 成品机器满速、**趋势** = 后半段 ÷ 前半段 (< 0.9 = 在往堵的方向走)、机器状态占比 (每 5 秒抽一次)、耗电。
     - **几条进料带要的料完全一样** (3 种以上、不含煤; 例: 组装机排近带 + 加长机械臂取的远带喂同一排机器) (2026-11-02 加): 分开放, 每道只放一种, 用量最大的先独占一条带 (内燃机: 管道一条带, 齿轮 + 钢材一条)。原来每条带每道轮流混放, 用量少的那种会堵住整道。结果里记 `splitStarts`。
     - 限制: 流体输入、采矿机、实验室、火车装卸不管 (记在 `unsupported`); "效率"按成品机器满速算, 上游配比不够的 (例: 太空第 7 张 2 台电炉供 1 台弹匣机, 21%) 是设计本身的配比, 不等于设计差; 商场类 (一堆机器各做一种成品) 效率没意义, 看开工率。
     - 试跑: Brian's City 第 16 张 (576 台电炉): 铁板每分钟 21337 / 满速 21600 = **98.8%**, 开工率 99%, 趋势 1.025, 耗电 115MW, 9985 件 25 秒 (6 分钟窗口)。
     - 第一次全量 (2.0 那批里第二层完整建成、有机器的 25 张): 测成 22、跳过 3。**简单模块测得准** (电炉阵列 97.5%、自举第 1 张 99.5%); **城市街区多数缺料或堵** (开工率 1%~15%): 它们靠火车卸货进料、很多中间品从别的街区来, 现在只在带子起点上料, 还模拟不了卸车臂 → 这批的"效率"不能当好坏标签。
     - 车站进料 (2026-11-02 加): 卸车臂 (取货目标为空 = 车厢位置, 往带子 / 箱子放) 每 tick 空手就塞一手 (按它实际的抓取数), 放什么按下游实际消耗的比例 (配方原料速度 + 烧煤机器的燃料速度, 从原型算; 第一次轮流放, 煤矿各半, 带子被煤堵满); 箱子再被机械臂放上带子的, 按带子往下游推; 带子下游已有"从箱子或车厢取货往上放"的, 起点不再额外喂 (不然一半运力被换成煤)。城市冶炼街区 (384 石炉): 效率 16% → **54.5%**, 剩下 45% 缺燃料 —— 不知道哪几节车厢装煤, 卸车臂只能按比例混着放, 已知限制。
     - 全量 (重跑后 31 张): 测成 28; 电炉街区按真实车站卸货测是 65.7% (之前在带子起点直接喂是 97.5%): 沙盘**不做研究**, 集装机械臂每手抓得少, 而这些后期设计默认研究过机械臂容量 → 车站卸货成了瓶颈。**测量条件 = 没研究加成**, 后期设计会被低估; 下一步加按研究等级测的选项 (`--research late`)。
     - **按研究等级测** (2026-11-02, `--research late`; `bp feed`、`dataset feed`、`search` 都有): 喂料前整个阵营研究完全部科技 (机械臂每手 4 / 12 / 16, facts inserter.hand-size-full-research), 数据集里存进 `feedLate` 一栏 (不覆盖不研究的 `feed`)。重测布莱恩城市 3 个车站进料的冶炼街区: 电炉冶炼 65.7% → **96.9%** (卸车臂抓取数就是原来的瓶颈); 电力铸钢 43.1% → 45.8% (趋势 1.47, 还在预热, 测量窗口不够长, 不是研究的问题); 烧煤冶炼 51.8% → 19.6% (变差: 卸车臂一手抓得多, 煤矿按比例混放的老问题更严重, 56% 时间缺燃料 —— 要先解决"哪节车厢装煤")。
     - 踩的坑 (都修了): 机械臂取放目标要过一个 tick 才算出来 (lab.md #56, 第一次全量 24 张全"找不到入口"); 测完不清场, 上一张 (朋友基地 1596 台机器) 一直运转、混进下一张的产量 (一张效率算出 756%); 装车臂放不出去就堵 → 当出口。
3. **评审**: 模型 (或人) 看蓝图和实测结果, 标"模块边缘 / 真错 / 好设计及原因"; 评语进思路库。

## 自己生成: 积木 + 搜索 + 沙盘打分 (2026-11-02 第一块: 冶炼列)
- 生成器 `tools/generators/smelter_column.py` (factorio-draftsman): 西出料带 | 出料臂 | 炉子 | 进料臂 | 中间进料带 (矿 + 煤) | 进料臂 | 炉子 | 出料臂 | 东出料带; 电线杆按 draftsman 里的供电半径 / 连线距离算 (区间覆盖贪心 + 连成一张网核对), 不手摆。参数: 炉子 (石 / 钢 / 电) × 机械臂 (普通 / 快速) × 带子 (黄 / 红) × 每边 8 / 12 / 16 座 = 36 个变体, 静态检查 0 错误。
- 打分: `npm run bp -- feed <书> --index all` (和数据集第三层同一套喂料实测), 出排名表 + JSON。36 个都不用补电。
- 结果 (预热 90 秒、测 120 秒, 每分钟铁板):

| 变体 | 每分钟 | 效率 | 每格每分钟 | 耗电 MW |
|---|---|---|---|---|
| 电炉 × 32 + 红带 | 1200 | 100% | 1.85 | 6.3 |
| 钢炉 × 24 + 红带 (**占地最省**) | 900 | 100% | 3.15 | 0.25 |
| 钢炉 × 32 + 红带 | 900 | 75% | 2.41 | 0.26 |
| 电炉 × 24 + 黄带 | 900 | 100% | 1.82 | 4.7 |
| 石炉 × 32 + 红带 | 600 | 100% | 1.60 | 0.18 |
| 石炉 × 24 + 黄带 | 450 | 100% | 1.57 | 0.14 |
| 钢炉 × 24 / × 32 + 黄带 | 450 | 50% / 38% | — | — |

- 结论 (沙盘量出来的, 和老玩家的经验一致): **瓶颈是"一道矿"**: 煤占一道时, 黄带一道矿每分钟 450 → 正好 24 座石炉或 12 座钢炉, 红带一道 900 → 24 座钢炉; 电炉不吃煤, 两道都是矿, 黄带 900 → 24 座、红带 1800 → 48 座。超过这个数多出来的炉子只是闲着。快速机械臂不加产量 (炉子慢, 普通机械臂够用), 只多耗电。→ 思路库 P-prod-01 补了这条。
- 下一步: 组装机排、车站、高架桥积木; 搜索不只网格穷举, 按指标往好的方向改参数; 赢家进数据集 (出处 generated, 许可 MIT)。

### 第二块: 组装机排 (2026-11-02)
- 生成器 `tools/generators/assembler_row.py` (draftsman; 和冶炼列共用 `gen_common.py`: 占地、电线杆规划、官方中文名): **按配方**出一排组装机, 1~2 种料一条进料带 (每道一种), 3~4 种料两条带 (近带用普通进料臂、远带用加长机械臂); 单排或镜像双排 (两排共用中间的进料带); 参数: 机器档、进料臂档、每台每条带几个进料臂、每台几个出料臂、带子档、每排台数。机械臂取放距离从原型读并核对布局假设; 流体原料的配方报"不支持"; 一行放不下的组合记 error 不进书。
- 静态检查 0 错误 (警告只有"蓝图边上的进出料带", 设计如此); 6 个试样喂料实测全部建成、没补电。
- 第一个发现 (沙盘): 不研究时快配方卡在机械臂上 —— 铁齿轮 (组装机2型每台满速每分钟 90) 用 1 个电力机械臂只到 30%; 实验 `inserter.hand-size-no-research` 量到没研究时四种机械臂每手都只抓 1 个。
- 用法: `lab-data/venv/Scripts/python -I tools/generators/assembler_row.py <输出> --spec <变体 JSON>` 或 `--grid <配方>`; 按指标找最好的用 `npm run search` ([search.md](search.md))。

## 出图 (给 AI 看图自查; 2026-11-02)
用户定的: 编辑器主要给 AI 用 —— 把设计渲染成图让 AI 看摆放和线路, 数据集每张配图; 给用户只看结论和预览链接。
```bash
npm run bp -- render <文件> [--index N] [--area x1,y1,x2,y2] [--check] [--out 图片] [--max 800] [--kb 300] [--plain] [--nogrid]
```

- 本机改进版 (2026-11-03): 编辑器副本上的本地分支 `pilot-local-2.1` (没推送上游) —— 游戏数据升到 2.1.24、默认中文界面 + 官方中文名、车厢方向 / 占地修正、实体和配方品质可改; 重新导出游戏数据时限制并行压缩 (`FBE_SPRITE_JOBS=8`, 32 路并行曾把内存耗尽, 拖垮了同时在跑的沙盘)。说明写在副本自己的 CLAUDE.md 顶部。公开仓库只放代码补丁, 不放导出的 data.json 和贴图 (游戏数据)。
- 安装: 克隆编辑器, 按它的说明装依赖 (要 npm 12), 打本机补丁 `git apply tools/fbe-patches/picture-frame.patch` (暴露出图画框, 坐标网格和标号靠它对位; 7 行) 和 `local-source.patch` (长蓝图预览链接用, 见下); `.env` 写 `FBE_DIR` (编辑器目录)。编辑器没开时命令自己用它的 `scripts/localpreview.mjs` 开, 用完关; 原来开着就不动。
- 输出 (CLAUDE.md 上限): 最长边 ≤800、≤300KB, 先 png, 超了换 jpeg 降质量, 再不行缩小。图上有蓝图坐标网格 (黄字, 间距按缩放取 1/2/5 进位, 线距 ≥40 像素); 信息层 (alt: 配方图标、机械臂方向、没配对的地下带) 默认开; `--check` 把静态检查的错 (红) 和警告 (橙) 画圈编号, 和命令行里的列表一一对应; `--area` 先把蓝图裁到这块再出图 (检查仍对整张做, 只标框里的, 免得裁剪边上出假错)。
- 坑: 载入后贴图异步到 (编辑器先发空贴图), 马上出图只有组装机和电线; 现在每 0.5 秒出一张小图算指纹, 画框和指纹连续两次不变才出正式图 (编辑器自己的 image-export 测试也是这么等)。信息层编辑器默认开, 按 Alt 是切换 (松开时生效)。
- **预览链接** (报告里给人看, 也是用户最后手动调整的入口): `npm run bp -- link <文件> [--index N] [--area …]`。≤2000 字的蓝图把字符串放进链接 (`#source=`, 不靠服务器); 更长的写进编辑器的本机目录 `packages/website/public/local-bp/<哈希>.txt`, 链接是 `http://localhost:8080/?source=http://localhost:8080/local-bp/<哈希>.txt`。要第二个本机补丁 `tools/fbe-patches/local-source.patch`: 编辑器把网址来源一律改写成 https 再经 `/corsproxy` 转给**公网上的官方代理**, 本机地址它够不着 (502), 也不该把本机地址发出去; 补丁让同主机的地址按页面自己的协议直接取。朋友基地 43 万字: 链接打开 4.2 秒载入 43125 件, 0 次经代理。
