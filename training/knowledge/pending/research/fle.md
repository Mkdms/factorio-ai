# 研究: Factorio Learning Environment (FLE)

> 2026-10-31 读了仓库 [JackHopkins/factorio-learning-environment](https://github.com/JackHopkins/factorio-learning-environment) (提交 e2a829d, v0.4.8) 和论文 [arXiv 2503.09617](https://arxiv.org/abs/2503.09617) (NeurIPS 2025 数据集赛道)。只读代码和文档, 没有运行。下文的路径都是 FLE 仓库里的相对路径。

## 一句话
FLE 是"评测大模型玩 Factorio"的环境: 模型每步写一段 Python 调用约 28 个工具建工厂, 按产量打分。最值得学的是**评测场的判分方法**和**沙盘工程上踩过的坑**; 它的动作执行方式 (带约束的上帝模式) 和支持的版本 (2.0 基础版) 都不适合我们的联机身体。

## 1. 怎么接游戏
- 无界面服务器 (Docker, 2.0.73, 可多开) + RCON; 没有正式模组, 运行时用控制台命令把每个工具的 Lua 注入 storage, 按 md5 只重传改过的脚本, 上传前本地查语法 (`fle/env/lua_manager.py`)。
- 启动时删掉太空时代、品质、高架铁路的数据 (`fle/cluster/run_envs.py`) → **不支持太空时代** (issue #211 无回应关闭)。火车、机器人、电路网络都没建模; 默认和平模式, 科技全开 (`fle/env/instance.py`)。
- 动作: 放置时检查背包和距离, 但用 `create_entity` 直接生成; 快速模式沿寻路结果瞬移、手搓瞬间完成, 应耗时间另记账 (`fle/env/tools/agent/move_to/server.lua`、`craft_item/server.lua`); 自动布线不限距离。
- 观察: 上一段程序的输出 (带行号) + 结构化状态: 实体状态枚举、警告、取放点、背包、科研、产量流, 可选渲染图。

## 2. 智能体接口
- 每步一段 Python, 逐句执行, 第一处错误就停, 报行号和"你是不是想用" (`fle/env/namespace.py`); 变量和函数跨步保留。
- 约 28 个工具: move_to; place_entity / place_entity_next_to / nearest_buildable; connect_entities (自动铺传送带、管道、电杆); pickup_entity、rotate_entity; insert_item、extract_item、inspect_inventory、craft_item; set_entity_recipe、set_research; nearest、get_resource_patch、get_entities、get_prototype_recipe; sleep、send_message、launch_rocket。
- **每个工具三个文件**: 手册 `agent.md` (用法和常见失败)、`client.py`、`server.lua`; 系统提示由函数签名 + 全部手册自动拼成。
- 记忆: 每 16 条消息总结成三段 (现有建筑和坐标、归类后的错误、自定义函数) (`fle/agents/formatters/recursive_report_formatter.py`); 另一种方案只保留固定 3 条消息的"状态面板"; 回溯智能体出错后回到上次成功处, 最多重试 8 次。
- 多智能体: 各有角色和变量空间, 用 send_message 通信; 任务有合作、内鬼、猜疑三种。自带一个 MCP (execute、render、状态 commit/restore/undo)。

## 3. 评测
- 实验室: 24 个吞吐任务 (固体每分钟 16、流体每分钟 250); **判分前放手 60 秒, 只计自动化产出**, 手搓和手采单独算并封顶 (`fle/eval/tasks/throughput_task.py`、`fle/env/utils/achievements.py`)。
- 开放玩法: 5000 步, 按配方递归给物品定价算产量分。
- 成绩: 论文 v1 (2025-03) Claude 3.5 Sonnet 实验室 21.9%; v0.3.0 (2025-09, 同一任务 8 次中成 1 次算过) Opus 4.1 过 16/24、GPT-5 过 15、Gemini 2.5 Pro 过 11; 内燃机、电池、轻质框架、处理器、蓝瓶、紫瓶、黄瓶没有模型做出。

## 4. 论文结论
- **空间推理差**: 摆得太挤或重叠, 不留接口; 原料超过 3 种就协调不了 6 台以上机器。
- **纠错差**: 成功的局里也有 56% 的步骤报错; 只查单个实体不查整体连接; 有模型连续 78 步重复同一个错误。
- **长程规划差**: 目标短视 (手搓 300 多个木箱), 用手搬和箱子中转代替自动化。
- **主要错误是对游戏状态认知错** (Opus 4.1 的错误 97.7% 属于这类), 不是代码写错。
- 有帮助的: 读错误日志自纠、运行时断言、持久变量; 模型很少自己建抽象。

## 5. 许可和活跃度
MIT (LICENSE 末尾附了说明, 所以 GitHub 显示 NOASSERTION; pyproject 写 MIT)。最后提交 2026-09-06 (v0.4.8), 仍有外部 issue。只支持 2.0 基础版。旁证: 有人用 Claude Code 通过 FLE 的 MCP 在 2.0 基础版发射了火箭, 但开了 10 倍速并大量用 RCON 绕过限制 ([Chadmonk/claude-code-plays-factorio](https://github.com/Chadmonk/claude-code-plays-factorio))。

## 6. 我们要学的 (前 5 条已写进设计)
1. **评测场**: "吞吐任务 + 放手 60 秒 + 只计自动化产出 + 同一任务跑多次统计", 作为"分数只许升不许降"的闸门; 错误按 语法 / 接口用法 / 状态认知 / 规划 分类, 画按步骤的错误率曲线; 内鬼和猜疑任务可测外交专家。
2. **io-lab 做成正式模组, 不在运行时注入脚本**: FLE 的注入导致无法存档、客户端一加入就崩、事件处理器互相覆盖 (issue #381、#417)。我们要让本机客户端连进沙盘, 所以: storage 只放数据, 对外用 remote 接口, 所有事件走同一个分发函数; RCON 每 4KB 响应约卡 40 毫秒, 大响应先在 Lua 里压缩 (1600 实体存档 10.5 秒降到 0.52 秒, `CHANGELOG.md` 0.4.8); 加连接存活检测, "没读到"不能当"读到空"。
3. **每个 MCP 配手册**: 用法 + 常见失败 + 带修复提示的报错 (例如"距离 X 超过上限 Y, 请靠近") + 实体状态枚举。
4. **记忆**: 固定状态面板 + 三段式报告; FLE 的主要错误是状态认知错, 所以专家每次调用都从世界模型重读, 工具返回动作后的真实状态。
5. **机制写成沙盘测试**: 照 `tests/invariants` 的写法, 每条机制一个引擎内测试, 注释引用 API 文档。FLE 的 2.0 迁移清单和火箭那局的经验作为第一批"待核实说法", 在 2.1 上验证, 例如: 炼油厂每个产物都要有出口; 油井产量衰减到 20%; 流体段长度约 320 格上限; 角色寻路把传送带当墙; get_entities 看不到中立实体、悬崖和树。

## 7. 不适合我们的
- 瞬移、瞬间手搓、不限距离布线: io-client 只能借接口的含义, 不能借实现; "动作耗时另记账"可以在沙盘里估算真人要花多久。
- connect_entities 超过约 50 格就不可靠: 长线用我们自己的寻路, 支持地下跳。
- 计算器: FLE 没有; 火箭那局里电力机械臂约每秒 0.83 个就卡住了组装机2型 → 我们的 calc 必须算机械臂和传送带速度。
- "模型写代码当动作"和我们"模型只说意图、MCP 执行"相反; 技术栈 (Python + Docker) 和版本 (2.0 基础版、和平模式、无战斗) 也不同, 只移植思路。

## 8. v0.3.0 页面补充 ([versions/0.3.0](https://jackhopkins.github.io/factorio-learning-environment/versions/0.3.0.html), 用户推荐)
- **评测设置**: 只评实验室任务; 定额固体每分钟 16、流体每分钟 250; 给模型 API 文档、配方、使用指南、固定背包; 最多 64 步, 可提前结束; 默认开推理; 主指标是"同一任务 8 次中成 1 次" (Pass@8)。v0.2.0 的回溯和反思逻辑这版不评。
- **框架**: 所有交互追加到同一段对话, 快到 token 上限时总结较早的历史; 不再依赖游戏客户端, 用无界面渲染; 接口符合 OpenAI Gym。
- **错误四分类**: 语法、语义 (接口用法理解错)、语用 (对游戏状态理解错)、规划和控制 (无法量化)。平均出错率: Claude Opus 4.1 22.99%, GPT-5 25.05%, Gemini 2.5 Pro 27.29%, Grok 4 40.89%。Opus 4.1 语法错误 0%, 语用错误占 97.7%; GPT-5 语法 21%, Grok 4 语法 17%; 语义错误 12–17%。
- **其他观察**: 出错率在中段上升 (工厂变复杂时); Grok 4 常陷入调试死循环, GPT-5 能较好恢复; 成功的模型很多靠手搬和箱子缓冲而不是真正自动化, 放手 60 秒的规则就是为了抓这种"刷分"。
- **作者列的下一步**: 人类基线、防刷分、按难度分级 (类似 METR)、更高的定额逼出真正的自动化、开放玩法和超大基地、实时游玩和延迟限制、多智能体协作、模组科技树、**键鼠加视觉的接口**、会进攻的敌人。

### 对我们的意义
- 作者列的下一步里, 键鼠加视觉的接口、敌人、实时、多智能体、大基地, 正是我们的 io-client、防务和总控要做的; 方向一致, 我们走在他们计划的前面。
- 评测场补三条: 定额分级 (从每分钟 16 往上加, 逼出真正自动化)、人类基线 (用户自己玩同一任务的成绩)、错误按四类统计并画按步骤的曲线。
- 模型的头号问题是"对状态理解错" → 我们的规矩 "专家每次从世界模型重读、工具返回真实状态" 是对症的。

## 9. 深挖: 无头运行和开发工具 (2026-10-31, 按版本风险筛选)
**结论: 这两部分都不能原样搬。** FLE 的代码绑 Docker 和 Linux, 锁在 2.0.73 基础版; 2.1 删掉了 `LuaEntity::fluidbox`、`LuaFluidBox`、`neighbours` 和旧的物品栏常量 (游戏 `data/changelog.txt`), FLE 的 Lua 用到 fluidbox 34 处、旧物品栏常量 39 处, 在 2.1.24 上跑不起来。能借的主要是方法。

### 9.1 它怎么做的
- **多开**: `fle cluster start -n N` 生成 docker-compose, 每实例一个 Linux 容器, RCON 端口 27000+i、游戏端口 34197+i, 每个限 1 核 1GB, 启动前查端口冲突 (`fle/cluster/run_envs.py`); 用异步队列分配实例 (`fle/eval/inspect/integration/simple_server_pool.py`)。
- **任务间重置**: 清掉玩家和中立实体、地上物品, 重设背包和科研, 只处理 1 号地表 (`fle/env/tools/admin/reset/server.lua`)。
- **压缩**: 0.4.8 起所有响应先在 Lua 里用 `helpers.encode_string` 压缩再加前缀发回, 1600 个实体的状态从 10.5 秒降到 0.52 秒 (`fle/env/tools/controller.py`)。
- **渲染器**: Lua 采集半径内的实体、水、矿, Python 用 PIL 分层画, 33 种实体专用画法, 输出 PNG 加坐标对应关系 (`fle/env/tools/admin/render/`)。贴图从一个没有声明许可的数据集下载, 版权归 Wube, 不在 FLE 的 MIT 里。
- **官方 API 说明: 无头模式下 `take_screenshot` 什么都不做**, 要真实画面必须用带图形的客户端。
- **工具**: `fle` 命令行 (起停集群、跑实验和评测、下载贴图); MCP 服务器 (执行代码、渲染、游戏状态的提交/回退/撤销); Gym 环境; Inspect AI 集成 (评分器、上下文方案对比、日志查看); 批量实验断点续跑 + W&B; SQLite/Postgres 存每步的程序和奖励; pass@k 分析和轨迹转视频; 只读监控面板; CI 起 4 台服务器并行测试。

### 9.2 我们怎么用
| 项目 | 做法 | 版本风险 |
|---|---|---|
| 产量分 | **直接用游戏自带的** `data/core/lualib/production-score.lua` (2.1.24 已按所有地表求和), 不借 FLE 的 | 版本无关 |
| RCON 压缩、前缀、忙时重试、重连 | 移植思路, TypeScript 几十行 | 版本无关 |
| 放手期判分、手搓和自动产出分开算并封顶、多次运行统计 | 移植思路, 只依赖产量统计 | 版本无关, 任务清单小改 |
| 多开编排和实例池 | 改成 Windows 原生进程: 每实例独立数据目录和端口 (先在沙盘实测) | 版本无关 |
| 实验记录、断点续跑、"存档 + 计划"版本库 | 移植思路, 用 Node 自带的 SQLite | 版本无关 |
| 任务间重置 | 移植思路, 按地表处理 (太空时代有多个星球和平台) | 小改即可 |
| 示意图渲染 | 自己写: 先按碰撞箱画色块和方向箭头, 不受版本影响; 真实画面用带图形客户端截图 | 采集端小改, 画法重写 |
| 实体状态存取、贴图下载、它的 MCP 和 Inspect 沙箱、面板 | 不用: 依赖已删除的接口、没有许可、或绑 Python/Linux | 要重写 |

**按性价比前 5**: ① RCON 压缩 + 忙时重试 + 存活检测 (约半天, 大批量读取快约 20 倍); ② 计分直接调游戏自带的 production-score, 加放手期和手搓/自动分开算, 作为评测场核心; ③ Windows 原生多开 + 实例池; ④ SQLite 实验记录 + 断点续跑 + 存档版本库; ⑤ 示意图渲染先画色块和箭头。
